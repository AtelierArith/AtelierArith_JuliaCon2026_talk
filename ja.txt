================================================================
[What I created]
================================================================

まず、私が何を作ったかをお話しします。

SubsetJuliaVM、通称 sjulia というものを作りました。

これは Julia の文法のサブセットをサポートする処理系で、Rust で実装したスタックベースの仮想マシン、VM です。

この VM は iOS と Android のデバイス上で動きます。

さらに、WebAssembly にコンパイルできるので、ブラウザの中でも動きます。

言語コアだけではなく、Plots.jl、OrdinaryDiffEq.jl、AbstractAlgebra.jl といったパッケージの一部もサポートしています。

[Deliverables]
================================================================

成果物は 3 つあります。

1 つ目は iOS / iPadOS のネイティブアプリです。JIT を一切使っていないので、App Store の審査に完全に準拠した形で、すでに App Store で公開されています。

2 つ目はソースコードです。julia-vm-oss という名前で GitHub に公開しています。

3 つ目は Web のプレイグラウンドです。ブラウザを開くだけで、インストールなしで sjulia を試せます。

「SubsetJuliaVM」で検索すると出てきますので、ぜひ後で試してみてください。

================================================================
[Why I created it]
================================================================

次に、なぜこれを作ったのかという話です。

動機はシンプルで、自分の iPad で Julia を動かしたかったからです。

ところが、Julia は通常 JIT コンパイルに依存する言語です。そして iOS は、この JIT を二重の意味でブロックしています。

1 つ目は OS レベルの技術的な壁です。W^X、Write XOR Execute と呼ばれる仕組みで、メモリページは「書き込み可能」か「実行可能」のどちらか一方にしかなれません。

JIT というのは、マシンコードをメモリに書き込んで、そこに飛んで実行するものです。つまり、書き込めて、かつ実行できるページが必要になります。

ところが、汎用の JIT は一般に配布されるアプリでは使えません。Apple はこれを Safari の JavaScript エンジンのような自社アプリのために確保しています。例外は、承認された代替ブラウザエンジンや、デバッガを接続した開発ビルドくらいです。これは私の思い込みではなく、Apple Platform Security の文書に書かれている公式のポリシーです。スライドにリンクを載せています。

2 つ目はストアの規約の壁です。App Store Review Guidelines の 2.5.2 で、アプリの機能を導入したり変更したりするコードをダウンロード・インストール・実行してはいけない、と定められています。

一方で、アプリに同梱したインタープリタは問題ありません。バイトコードは、署名済みのアプリが読む「ただのデータ」だからです。ちなみに、ダウンロードしてきたコードは、解釈実行であっても 2.5.2 の対象になり得ます。

[What about Binder or Google Colab?]
================================================================

「Binder や Google Colab を使えばいいのでは?」と思われるかもしれません。

しかし、これらはインターネット接続が不安定な場所では使いものになりません。移動中の電車の中や、回線の弱い会場などですね。

また、外部パッケージのインストールに時間がかかるという問題もあります。

そこで、端末の中で完結して、オフラインで動く Julia 環境が欲しい、と考えました。

================================================================
[How I created it]
================================================================

では、どう作ったかです。

iOS には Pythonista や Carnets といった、Python が動くアプリがすでに存在します。

これらが動くということは、JIT を使わないインタープリタなら iOS でも動くということです。それなら、Julia の文法を受け付ける仮想マシンを自分で作ればいいのではないか、と考えました。

とはいえ、正直に言うと、これを一人で作りきる能力は私にはありません。

そこで AI に頼ることにしました。Claude Code、Codex、Cursor、DeepSeek、Kimi といった AI ツールをフル活用して開発しています。

================================================================
[Let's actually build it!]
================================================================

実際に作ってみました。

中身は、JIT を使わないスタックベースのバイトコードインタープリタです。

処理の流れはスライドの図のとおりです。Julia のソースコードをパースして CST、構文木を作り、Lowering で Core IR という中間表現に変換し、コンパイラでバイトコードに変換する。ここまでが実行前です。実行時には、スタック VM がそのバイトコードを解釈して結果を返します。

その結果が、GitHub で公開している AtelierArith/julia-vm-oss です。

================================================================
[How sjulia differs from official Julia]
================================================================

公式の Julia と sjulia がどう違うのか、コードの解釈・実行の各ステージで比較してみます。表の各セルは「誰がやるか → 何を作るか」という形式で書いています。

パースについて。公式は flisp、あるいは JuliaSyntax.jl が AST を作りますが、sjulia は pure Rust のパーサが CST を作ります。

Lowering について。公式は lowered IR に変換しますが、sjulia は Rust 実装の Lowering が Core IR に変換します。

コード生成が一番大きな違いです。公式は実行時に LLVM の JIT がネイティブコードを生成します。一方 sjulia は、バイトコードコンパイラが、実行前にバイトコードを生成し終えます。

実行について。公式は CPU がネイティブコードを直接実行しますが、sjulia はスタック VM がバイトコードを解釈実行します。

ランタイムライブラリについて。公式は C のランタイムと pure Julia の base からなりますが、sjulia は Rust のビルトインと、pure Julia で書いた Base のサブセットで構成しています。

ポイントは、JIT が一切ないことです。実行時にネイティブコードを生成しないので、W^X 制約のある iOS でも、WASM でも動く、というわけです。

================================================================
[What SubsetJuliaVM does not provide]
================================================================

逆に、SubsetJuliaVM が提供しないものも正直にお話しします。サンドボックスで、オフラインで、コードをダウンロードしない、というモデルを壊すものは全部ありません。

まず Pkg.jl、パッケージ管理はありません。Pkg.add もレジストリもダウンロードもなくて、using で使えるのはバイナリに同梱された約 34 個のパッケージだけです。

ネットワーク I/O もありません。Sockets も Downloads も HTTP もなしです。

ファイルシステムへのアクセスもありません。include は、埋め込まれた仮想パスを通して解決されます。

外部プロセスの起動、run もありません。

C インターフェース、ccall や pointer、unsafe 系もありません。

本当の並列実行もありません。設計としてシングルスレッドで、Task や Channel は協調的な継続として実装されています。

ネイティブコードのリフレクション、code_llvm や code_native もありません。そもそも LLVM がいないので。代わりに sjulia --dump-bytecode でバイトコードを見ることができます。

詳しくは Appendix のスライドにまとめてあります。

[juliars]
================================================================

もうひとつ、実験的な機能を紹介します。juliars です。

これは Julia から Rust へのトランスパイラです。Julia のコードを Rust のソースコードに変換して、ネイティブバイナリとしてコンパイルします。

JuliaC という AoT コンパイルの仕組みが公式にもありますが、juliars は libjulia を必要としない、という点が異なります。生成されるのは完全にスタンドアロンなバイナリです。

同じマンデルブロの例を juliars でコンパイルして実行すると、計測部分の実行時間は 9.4e-5 秒。VM での実行と比べて桁違いに速くなります。

================================================================
[Performance: Julia vs. SubsetJuliaVM]
================================================================

性能をもう少しきちんと比較します。

ベンチマークはマンデルブロ集合の計算です。1500 x 1500 のグリッドで最大 500 イテレーション。すべての処理系で同一のソースコードを使っています。Apple Silicon の macOS で、2026 年 7 月に計測しました。

結果はこうです。

公式の Julia が 0.50 秒。

juliars の AoT が 0.52 秒。公式の Julia とほぼ同じ速さです。

sjulia の VM は 4.0 秒。公式の 8 倍程度ですが、インタープリタとしては十分実用的な速度です。

参考までに Python 3.14 は 20.8 秒でした。VM 実行でも Python の 5 倍速い、ということになります。

まとめると、AoT なら公式の Julia 並みの速度が出て、VM でもインタープリタとして十分速い、という結果です。
