[What I created]
================================================================

First, let me tell you what I built.

I created something called SubsetJuliaVM — or "s-julia" for short.

It's a language runtime that supports a subset of Julia's syntax: a stack-based virtual machine, implemented in Rust.

This VM runs on iOS and Android devices.

And because it compiles to WebAssembly, it also runs right inside the browser.

It's not just the language core — it also supports parts of packages like Plots dot j-l, OrdinaryDiffEq dot j-l, and AbstractAlgebra dot j-l.

================================================================
[Why I created it]
================================================================

So, why did I build this?

The motivation is simple: I wanted to run Julia on my own iPad.

But here's the problem. Julia normally relies on JIT compilation — and iOS blocks JIT twice over.

The first wall is technical, at the operating-system level. It's a mechanism called W xor X — "write xor execute". A memory page can be writable, or executable, but never both.

Now, a JIT works by writing machine code into memory and then jumping into it to execute. So it needs pages it can write and then execute.

And general-purpose JIT is simply not available to ordinary distributed apps. Apple reserves it for its own apps, like Safari's JavaScript engine. The only exceptions are approved alternative browser engines and development builds with a debugger attached. This isn't my speculation — it's Apple's officially documented policy, in the Apple Platform Security guide. The link is on the slide.

The second wall is the store policy. App Store Review Guidelines, section two point five point two, says apps may not download, install, or execute code that introduces or changes app functionality.

On the other hand, a bundled interpreter is perfectly fine. Bytecode is just data, read by an app that has already been signed. By the way, downloaded code can still fall under section two point five point two, even if it's only interpreted.

================================================================
[What about Binder or Google Colab?]
================================================================

You might be thinking: "Why not just use Binder or Google Colab?"

Well, those are unusable anywhere the internet connection is unreliable — on a moving train, or in a venue with weak Wi-Fi.

Installing external packages also takes a long time.

So I wanted a Julia environment that is self-contained on the device and works completely offline.

[How I created it]
================================================================

So, how did I build it?

On iOS, apps like Pythonista and Carnets — which run Python — already exist.

The fact that they work means an interpreter with no JIT can run on iOS. So I thought: why not build a virtual machine that accepts Julia syntax?

To be honest, though, I don't have the ability to build this all by myself.

So I decided to lean on AI. I built it with heavy use of AI tools: Claude Code, Codex, Cursor, DeepSeek, Kimi, and others.

================================================================
[Let's actually build it!]
================================================================

And I actually built it.

Under the hood, it's a stack-based bytecode interpreter — no JIT.

The flow is what you see in the diagram. Julia source code gets parsed into a CST — a concrete syntax tree. Lowering turns that into an intermediate representation called Core IR. The compiler turns that into bytecode. All of that happens before execution. At run time, the stack VM interprets the bytecode and produces the result.

The result of all this is on GitHub: AtelierArith slash julia vm oss.

================================================================
[How s-julia differs from official Julia]
================================================================

How does s-julia differ from official Julia? Let's compare stage by stage — how code is interpreted and executed. Each cell in this table reads as "who does it, and what it produces".

Parsing. Official Julia uses flisp, or JuliaSyntax dot j-l, to produce an AST. S-julia uses a pure-Rust parser that produces a CST.

Lowering. Official Julia lowers to its lowered IR. S-julia's Rust lowering produces Core IR.

Code generation is the biggest difference. Official Julia generates native code at run time, with the LLVM JIT. S-julia's bytecode compiler generates bytecode before execution.

Execution. In official Julia, the CPU runs native code directly. In s-julia, the stack VM interprets bytecode.

The runtime library. Official Julia is a C runtime plus the pure-Julia base library. S-julia is Rust builtins plus a pure-Julia subset.

The key point: there is no JIT anywhere. No native code is generated at run time — and that's exactly why it runs on iOS with its W xor X restriction, and on WebAssembly.

================================================================
[What SubsetJuliaVM does not provide]
================================================================

To be fair, let me also be honest about what SubsetJuliaVM does not provide. Everything that would break the sandboxed, offline, no-downloaded-code model is simply absent.

There's no Pkg dot j-l — no package management. No Pkg dot add, no registry, no downloads. "Using" only reaches the roughly thirty-four packages bundled into the binary.

There's no network I O. No Sockets, no Downloads, no HTTP.

There's no filesystem access. File operations are unimplemented; "include" resolves through virtual embedded paths.

No external processes — no "run".

No C interface — no c-call, no pointer, no unsafe operations.

No real parallelism. It's single-threaded by design; Tasks and Channels are implemented as cooperative continuations.

And no native-code reflection — no code-LLVM or code-native, because there is no LLVM. Instead, you can inspect the bytecode with "s-julia dash dash dump bytecode".

The details are all in the appendix slides.

================================================================
[juliars]
================================================================

Let me also introduce one experimental feature: juliars.

It's a Julia-to-Rust transpiler. It converts Julia code into Rust source code and compiles it into a native binary.

Official Julia has an ahead-of-time story called JuliaC, but juliars differs in that it does not need lib-julia. What you get is a completely standalone binary.

Compiling the same Mandelbrot example with juliars and running it, the measured part takes about nine point four times ten to the minus five seconds — roughly ninety microseconds. Orders of magnitude faster than running on the VM.

================================================================
[Performance: Julia vs. SubsetJuliaVM]
================================================================

Let's compare performance a bit more carefully.

The benchmark is the Mandelbrot set: a fifteen-hundred by fifteen-hundred grid, up to five hundred iterations. The exact same source code runs on every implementation. Measured on Apple Silicon macOS, in July twenty twenty-six.

Here are the results.

Official Julia: zero point five seconds.

Juliars, ahead-of-time: zero point five two seconds — essentially the same speed as official Julia.

The s-julia VM: four seconds. That's about eight times slower than official Julia, but for an interpreter it's very much a practical speed.

For reference, Python three point fourteen took twenty point eight seconds. So even running on the VM, we're about five times faster than Python.

To sum up: with ahead-of-time compilation you get official-Julia-level speed, and even the VM is fast for an interpreter.
